# WeDB vs WeDb-BfTree vs RocksDB vs Fjall 深度性能评测基准报告

## 1. 评测硬件环境与规格配置

- **写入操作规模: 顺序 150,000 ops / 随机 150,000 ops**
- **读取操作规模: 150,000 ops**
- **单条记录数据载荷: 128 字节**
- **对齐物理内存预算: 256 MB (各存储引擎严格 1:1 字节级对齐)**
- **评测模式: 纯底层存储引擎端到端公平对决（零侧边外置缓存，杜绝纯内存结构虚假跑分）**

## 4. 关键指标深度技术归因与剖析

1. 热点就地更新: WeDB 展现出碾压级别的性能优势。HybridLog 在内存中划定了「可变区」，对已有键执行同长更新直接进行就地指针修改，无需分配新日志槽位、无需写入 WAL、无需多层压缩合并；而 LSM 架构（RocksDB 与 Fjall）每次更新必须先追加 Memtable，后续引发级联 Compaction 与高倍写放大。

2. 点读命中: WeDB 基于 64 字节 Cacheline 对齐的无锁哈希索引，在内存中直接根据 14 位 Tag 和桶内哈希定位到指针，时间复杂度为纯粹的 O(1)，无跳表或多层树遍历；WeDb-BfTree 通过内存页缓存定位 B 树节点；RocksDB 与 Fjall 则需经过 Memtable 查找或 BloomFilter + Block Cache 检索，路径明显较长。

3. 多线程并发横向扩展: WeDB 的 LightEpoch 提供全无锁线程协调机制，各线程拥有独立的 Session，原子 CAS 保证无锁竞争；WeDb-BfTree 采用条带锁并发；RocksDB 在并发写入时受互斥锁批处理协调制约，高并发下 WeDB 展现出极高线性扩展性。

4. 有序范围查询: 各引擎展示了不同存储设计的技术权衡。WeDb-BfTree 是我们参考微软 Garnet bftree-garnet 设计自研的块级有序 B-树引擎，在块级分页和叶子缓存协同下，范围查询吞吐位列全场第一；RocksDB 与 Fjall 支持全量持久化键的字典序连续范围扫描；WeDB 则将范围排序能力解耦至对象层跳表（SortedSet），在内存缓存中提供亚微秒级的排名与区间切片。
