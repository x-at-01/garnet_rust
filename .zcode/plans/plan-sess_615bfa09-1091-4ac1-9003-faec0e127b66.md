# BfTree 持久化实施计划（对标 ../garnet/）

## 背景与目标
共享 BfTree（承载 Flattened ZSet 成员数据 + ACL/集群元数据）当前落在 /tmp 临时文件且 Drop 时删除，checkpoint 不覆盖它，服务器 SAVE 只 flush、启动从不恢复 → 重启全丢。本次按 Garnet RangeIndex 树的四层持久化机制改造：**持久工作文件 + checkpoint CPR 快照 + 恢复预置拷贝 + 原地换树 + 写入屏障**。范围：crate 层 + 服务器接线（用户已确认）。

关键已验证事实（决定设计）：
- `BfTree::with_config` 永远建新树（fresh root），对已存在文件续开=逻辑丢数据 → 打开已有工作文件必须走 `new_from_cpr_snapshot`。
- `new_from_cpr_snapshot` 把快照文件**绑定为活动基文件**（bf-tree snapshot.rs:1202-1203）→ 恢复必须先 `fs::copy` 快照到工作路径再打开，绝不能直接从会被 `purge_checkpoint` 删除的 token 目录打开（Garnet RebuildFromSnapshotIfPending 的 File.Copy 同理）。
- checkpoint meta 的 `StoreMeta.bftree_path/range_index_dir` 已持久化但 `recover()` 从未回填 config（既有缺口，顺手修复）。

## 改动清单

### 1. `wedb_bftree/src/service.rs` — 写入屏障 + 原地恢复
- `BfTreeService` 新增字段：`writers: AtomicUsize`（活动写者数）、`snapshotting: AtomicBool`（快照进行中）。
- RAII 写者守卫：`insert`/`delete` 顶部获取（若 `snapshotting` 先自旋等待，再 `fetch_add`；drop 时递减）——零调用方改动，ACL 等一切持有者自动纳入屏障（对标 Garnet barrier，消除"树新于 hlog 截断点"的分数漂移）。
- `cpr_snapshot`：置 `snapshotting` → 自旋等 `writers==0` → 执行底层快照 → 清标志（对标 `SnapshotUnderClaim`）。
- 新增 `recover_in_place(&self, path) -> Result<()>`：`tree.write()` 下用 `BfTree::new_from_cpr_snapshot(path, true, None, None, None)` 换入恢复树并更新 `file_path`/`storage_backend`。ACL 持有的 `Arc<BfTreeService>` 无需重绑。

### 2. `wedb_store/src/store.rs` — 工作文件持久化
- `init_bftree`：`bftree_path` 存在 → `BfTreeService::recover_from_cpr_snapshot(path, true, Disk)`；失败（新鲜 open_disk 产生的无魔数文件或损坏）→ `warn` + 删除该文件 + 走 fresh `open_disk`；不存在 → 现状 `open_disk`。

### 3. `wedb_store/src/checkpoint.rs` — 共享树快照/恢复（镜像 RangeIndex 两函数）
- `take_bftree_checkpoint(&self, dir, token) -> Result<usize>`：`store.bftree.cpr_snapshot({dir}/{token}/bftree/shared.bftree)`；`bftree_path` 为 None（临时内存树）时跳过返回 0。
- `recover_bftree_from_checkpoint(&self, dir, token) -> Result<()>`：token 快照存在 → `fs::copy(快照 → 工作路径)` 预置 → `bftree.recover_in_place(工作路径)`；不存在 → 保持 init 时已从工作文件恢复的状态。

### 4. `wedb_checkpoint/src/manager.rs` — 接线
- `create_checkpoint_with_token`：step 5（RangeIndex 快照）之后、step 5.1（`sync_dir_tree`）之前插入 `store.take_bftree_checkpoint(dir, token)?`——一次递归 fsync 同时覆盖两个子目录树；失败致命传播（对标 Garnet 快照失败 fatal）。
- `recover`：config 回填 `meta.store_meta.range_index_dir` 与 `bftree_path`；`recover_range_indexes` 旁追加 `store.recover_bftree_from_checkpoint(dir, token)?`。

### 5. `wedb_server` — SAVE/BGSAVE/启动恢复
- `context.rs`：
  - store_config 增加 `.with_bftree_path({dir}/bftree/shared.data.bftree)`；日志文案同步修正"自适应配置"失实问题（顺带把 `default()` 换成 `auto()`，与日志语义一致）。
  - 启动顺序：`CheckpointManager::recover_latest({dir}/checkpoints, device)` 成功 → 用恢复的 store；`NoValidCheckpoint`（无任何 checkpoint）→ 现状 `WedbStore::open`。
  - `ServerContext` 新增 `checkpoint_dir: PathBuf` 与 `last_save_ms: AtomicU64`。
- `dispatcher.rs`：
  - SAVE → await `create_checkpoint(store, checkpoint_dir, CheckpointType::FoldOver)`，成功后更新 `last_save_ms` 回 OK；失败回 ERR（对标 Garnet 快照失败致命语义，向前端暴露）。
  - BGSAVE → `spawn` 同路径后台执行，立即返回 started。
  - LASTSAVE → 返回真实 `last_save_ms`（秒）。
- `wedb_server/Cargo.toml` 若缺 `wedb_checkpoint` 依赖则 `cargo add wedb_checkpoint --path wedb_checkpoint`。

### 6. 测试与验收
- `wedb_checkpoint/tests` 新增端到端用例：tempdir + bftree_path；ZADD ~150 个 >64B 成员触发 promote 进 BfTree；写 ACL 前缀键；`create_checkpoint` → drop 全部 → `recover_latest` → 校验 ZSCORE/ZRANGE/ZCARD 与 ACL 键全部存活；`purge_outdated(1)` 后二次恢复仍成功（验证恢复后的活动基文件在预置路径、不在 token 目录）。
- `wedb_store/tests`：`init_bftree` 对无效格式工作文件的容错重建（垃圾字节 → open → fresh 树 + 旧文件被替换）。
- 每完成一步跑 `sh/clippy.sh` 清警告；全部完成后 `./test.sh` 通过为验收线。
- 按 AGENTS.md：开发完成后开子代理读取 `.agents/skills/rust_review` 规范做审查与优化。
